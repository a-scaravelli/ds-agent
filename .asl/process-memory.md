- **Decisioni**: storage is SQLite through the standard library, behind the replaceable `Registry` interface, as the source of truth. Judged against the criteria of section 1: no network and no new dependency (works offline, tests run on `:memory:` or `tmp_path`), low maintenance (stable stdlib API, nothing to pin or upgrade), reproducibility (deterministic ordering, inspectable file) and integrity (UNIQUE fingerprint and transactions enforce deduplication and referential integrity). Following your answers: the fingerprint includes the code hash; dedup runs only in `add_attempt` against all earlier attempts (any cycle, any outcome); code fixes are extra execution records of the same attempt and do not consume iterations; the cap is 1 + `max_fix_retries` executions (3 fix retries by default, per cycle); the attempt outcome is that of its last execution; `failure_kind` is required unless `succeeded` and absent otherwise. Assumptions to confirm in review: `add_execution` accepts a rerun only after a `failed/code_error` execution; `close_attempt` refuses an attempt with no executions, an already closed one, and a `code_error` one before the cap (so attempt-level `code_error` means "still failing after the cap"); open attempts are excluded from outcome and failure queries; `reason` is required only for non-succeeded runs and `metrics` must be non-empty for succeeded ones; the cycle `state` is free non-empty text until the loop ticket; the caller computes the fingerprint (the frozen-protocol hash is not stored on the cycle here); `inconclusive` appears in `list_failures` when closed. Open point recorded in section 7: an iteration recorded `inconclusive` after repeated rejected proposals has no execution and no fitting `failure_kind`, to be settled in the loop ticket. The semantic level of deduplication is not implemented. Single process assumed. ## Ticket #10 – Implement ticket 3 of docs/design.md: evaluation engine with frozen split
- **Giro**: 1
- **Data**: 2026-10-17
- **Cosa è stato fatto**: implemented ticket 3 of section 15 in `src/kaggle_agent/evaluation/`: `protocol.py` (immutable `Protocol`, all fields mandatory), `metrics.py` (`METRICS`, `register_metric`, each metric declares its natural direction), `schemes.py` (`SCHEMES`, `register_scheme`; `random` with optional stratification, `group`, `chronological`), `split.py` (`FrozenSplit` exposing only development partitions, `HoldoutAccessor` with the single holdout session), `threshold.py` (`dispersion`, `compare`), `hashing.py` (`evaluation_code_hash`, `protocol_hash`), `engine.py` (`EvaluationEngine`, `Candidate`, `freeze`, `verify`, `evaluate_validation`, `compare`, `holdout_session`) and `errors.py`. Minimal additive changes to `registry`: `Cycle.protocol_hash` with `set_protocol_hash` (write once), `HoldoutSession` and `HoldoutRead` (append-only log), `ComparisonRecord` with `count_comparisons`; SQLite file of ticket 2 are migrated with `ALTER TABLE`. `pyproject.toml` pins pandas, numpy and scikit-learn with `==`. Docs: `docs/design.md` (sections 1, 5, 6, 7, 14, 15, 16), `README.md` (evaluation section with an example, known limits), `.asl/test-map.json` (keys 1-47, the plan's cases). The branch already had earlier commits for this ticket; this round added the documentation, the design/README tests and the test map.
- **Decisioni**: libraries judged on the criteria of section 1 (Mac without GPU, free, offline, low maintenance, reproducible with a seed). pandas + numpy + scikit-learn chosen (confirmed by the user): the metrics and partition primitives are well tested and deterministic for a seed. Rejected: pure Python (error-prone ties, stratification, edge cases, no benefit), polars/pyarrow (further from the stack of generated code and Kaggle notebooks, no need shown), scipy alone (statistics but no ready partitioning or metrics). LightGBM and MLflow left out of this ticket. Threshold: one parametric form, mean paired difference oriented by the metric direction must exceed `k` × sample standard deviation (ddof=1) of the baseline over all partitions; `k` comes from the protocol, no default; comparisons are stored and counted but the threshold does not grow with the count yet. Protocol hash: protocol content plus SHA-256 of the `.py` sources of `evaluation`, computed at runtime (no manual version constant), stored on the cycle at `freeze()` and rechecked before every evaluation and holdout read; library versions are outside the hash and recorded in `resources`. Metric and scheme never have a default; the direction is explicit in the protocol and only checked against the one declared by the metric. Deterministic schemes accept repetitions: identical folds, only the candidate seed changes, so the baseline dispersion measures model-seed noise. Holdout: one session per cycle (best attempt plus user-requested variants), each read logged in the registry before the data is returned, one read per attempt, no reopening even after closing, a failed evaluation still consumes the session. To reconfirm: a candidate exception that leaves the session block makes the remaining variants unevaluable in that cycle (the caller must handle errors inside the block if it wants otherwise); the engine does not check that the attempt read is the best one (left to report/review, ticket 10). Known limits: the holdout guarantee is interface plus log only, real isolation comes with the sandbox (ticket 6); the hash depends on the bytes of the sources, so any edit of the package (even a reformat or different line endings) invalidates the frozen protocols of open cycles, and a library change in the middle of a cycle is recorded but not blocked; session rules read-then-write are safe for a single process only. The engine returns the execution record but does not persist it (the loop ticket does, and must also call `freeze()` at approval). No defect found in the code.
